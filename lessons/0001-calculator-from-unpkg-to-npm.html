The calculator: from unpkg to npm + Vite

Lesson 0001 · Phase 1: Node.js and npm

Session approx. 75 min Needs Node 24, the calculator project, git Plan learning plan Cheat sheet package.json, npm, Yarn

Win of the day: the student's calculator starts with npm run dev. It loads Scale from node_modules, not from unpkg. The student can say what each line of the new package.json does.

Why this lesson matters for Scale: Scale is a package on npm, and a project of many packages. Every contribution starts with package.json, an install, and a script. The calculator is a small, safe place to learn this before the large repo.

1 · Warm-up recall (5 min, no notes)

Answer from memory. Do not look anything up.

  1. In your calculator, which tags load Scale? From where?
  2. What is the difference between <script> and <script type="module">?
  3. In one sentence: what is Node.js?

Ask the questions. Do not correct yet; only listen. The answers show what the student really knows from the self-study.

2 · Three ideas (15 min)

Idea 1 — unpkg and npm deliver the same files

The student's page loads a URL like this:

https://unpkg.com/@telekom/scale-components@next/dist/scale-components/scale-components.esm.js

This URL has three parts: the package name @telekom/scale-components, a version or tag next, and a path inside the package. unpkg is a CDN that serves files from the npm registry (unpkg.com). npm install downloads the same package into node_modules/, so the same file is now at:

node_modules/@telekom/scale-components/dist/scale-components/scale-components.esm.js

The Scale package.json has "unpkg": "dist/scale-components/scale-components.esm.js". This is the file unpkg serves if the URL has no path.

Idea 2 — package.json is the manifest of a project

It records the project name, the scripts, and the packages with their allowed versions. dependencies are needed at runtime; devDependencies are needed only to develop and build (npm docs). The lock file records the exact installed versions, so every machine installs the same tree (npm docs).

C++ analogy: package.json ≈ a CMakeLists with a dependency list; the lock file ≈ pinned versions in a vcpkg/Conan lock.

Idea 3 — the browser does not know node_modules

The browser needs a URL for every import. A bare specifier like '@telekom/scale-components/loader' is only a name, so the browser cannot load it alone (MDN: JavaScript modules). A tool such as Vite resolves names to files in node_modules. Vite also gives a fast dev server and a production build in dist/.

3 · Student exercise (40 min)

Let the student type every command. Ask "what do you expect?" before each command and "what changed?" after it. This prediction step is where learning happens.

Checked on 2026-10-02 with Node 24.18, npm 11.16, Vite 8.3 and Scale 3.0.0-beta.161: the steps work in dev mode and in a build, with no Vite config.

  1. Check the tools. Node must be 24.x (Scale needs 24). 
    node -v
npm -v
  2. Go to the calculator folder. Make a git commit of the current state, so you can compare later. 
    git add -A && git commit -m "chore: state before npm"
  3. Make a package.json. Open it and read each field. 
    npm init -y
  4. Look at the tags on npm before you install. Compare latest and next. 
    npm view @telekom/scale-components dist-tags
    Check your answer (open after you ran the command)

    On 2026-10-02: latest: 3.0.0-beta.161 and next: 3.0.0-beta.156. So @next is older than @latest, but the Scale README says to install @next. This is a real documentation bug — a good candidate for a very small first PR later (see the plan).

  5. Install Scale as a runtime dependency and Vite as a dev dependency. 
    npm install @telekom/scale-components
npm install -D vite
    Now open package.json, package-lock.json and node_modules/@telekom/scale-components/package.json. Find the fields unpkg, module and types.
  6. Add three scripts to package.json: 
    "scripts": {
  "dev": "vite",
  "build": "vite build",
  "preview": "vite preview"
}
  7. Remove the unpkg <link> and <script> tags from index.html. Make sure the main script tag has type="module", e.g. <script type="module" src="./main.js"></script>.
  8. At the top of the main JS file, load Scale from the package. This is the official way from the Scale README: 
    import '@telekom/scale-components/dist/scale-components/scale-components.css';
import { defineCustomElements } from '@telekom/scale-components/loader';

defineCustomElements(window);
  9. Start the dev server and open the URL it prints (normally http://localhost:5173). Do not open index.html with a double-click (file://). 
    npm run dev
    The calculator must work as before. Open DevTools → Network: the Scale files now come from localhost, not from unpkg.
  10. Make a production build and look into dist/. Why are there many *.entry-*.js files? (Hint: Stencil loads each component only when the page uses it — "lazy loading".) 
    npm run build
npm run preview
  11. Add a .gitignore with node_modules/ and dist/. Commit. Look at git diff HEAD~1 --stat.
  • Calculator runs with npm run dev
  • No unpkg URL left in the project
  • node_modules/ is not in git; package-lock.json is in git
  • The student explains each line of package.json

4 · Check (10 min)

The student answers alone. The quiz gives feedback at once.

Without Vite, a plain module script does import … from '@telekom/scale-components/loader'. What happens?

Why is Vite in devDependencies, but Scale in dependencies?

Which one must you commit to git?

In @telekom/scale-components@next, what is next?

Watch for these errors:

  • Page opened with file:// → imports fail. Use the URL from npm run dev.
  • node_modules/ committed → remove it, add .gitignore.
  • Old unpkg tag still in index.html → components load twice; the console shows "already defined".
  • npm warn … lines are not errors. Read them, but they do not stop the install.

Evidence of learning (for a learning record): the student predicts correctly what step 9 shows in the Network tab, and explains why without help.
