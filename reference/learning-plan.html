Weekly learning plan

From browser JavaScript to a first bug fix in Telekom Scale · 8 weeks · 6–10 h each week · one sync each week

First read How to work with this plan This week week 1 All sources RESOURCES.md

The goal after 8 weeks: you open a pull request to telekom/scale that fixes a small bug. It has a test, a Conventional Commit message, and it passes the CI checks.

Where you start

  • Your calculator works (HTML + JS + JSDoc types). It loads Scale components from unpkg. It is in git and pushed.
  • You read: "What is a package manager?" (first section), "What is npm" (and set up Node.js and npm), and javascript.info: An Introduction to JavaScript.
  • You know C++ and OOP. Many ideas will look familiar. npm is like NuGet in the C# world: it gets libraries for your project.

The 8 weeks

Each week has its own handout with all details. You get it at the sync. The overview below shows the path. Each week builds on the week before.

Week 1

npm and Vite: the calculator moves to npm

learn what Node.js does · package.json · dependencies vs. devDependencies · npm scripts · lock file · dist-tags · ES modules and bare imports · what a dev server and a bundler do

build the calculator gets Scale from npm, starts with npm run dev, and builds with Vite. You do it on a branch and merge it with a pull request in your own repo.

No unpkg URL left; you explain each line of your package.json.

Week 1 handout →

Week 2

Node.js as a tool; real package.json files

learn promises and async/await · reading files with Node · ES modules vs. CommonJS · semver ranges (^, ~, beta versions) · npm script hooks (pre/post)

build a Node script npm run report that lists your dependencies: the range in package.json and the installed version. A table that explains each script in the Scale root and packages/components package.json.

Your Node script works; you explain the Scale scripts.

Week 3

The toolchain; Scale on your machine

learn bundler, transpiler, formatter, linter · Yarn 1 vs. npm · workspaces and monorepos · Lerna · forks and the upstream remote · WSL2 (Windows)

build fork and clone Scale, yarn bootstrap, start the component dev server, change one text locally and see it reload

Scale runs on your machine; you explain what yarn bootstrap and yarn start do.

Week 4

TypeScript for a C++ programmer

learn structural typing (the big difference to C++) · everyday types · interface and type · unions and narrowing · generics (vs. C++ templates) · tsconfig.json and strict · types are removed at runtime

build the calculator moves from JSDoc to TypeScript; npm run typecheck passes in strict mode

Calculator in TypeScript, no any, no type errors.

Week 5

Web Components in depth

learn JS classes (fast for you) · custom elements · Shadow DOM · <slot> · :host and ::part() · CSS custom properties and design tokens · custom events (the Observer pattern)

build your own custom element <calc-history> in TypeScript for the calculator. Inspect scale-button in DevTools: shadow root, parts, --telekom-* tokens.

Your component works and sends an event; you show the same parts in a Scale component.

Week 6

StencilJS: read and change Scale components

learn decorators · @Component, @Prop, @State, @Event, @Watch, @Element · JSX render() · <Host> · component lifecycle

build rebuild <calc-history> with Stencil and compare. Explain divider.tsx line by line. Read two small merged Scale fixes and explain them.

Stencil version works; you explain a real Scale component and a real fix.

Week 7

Tests and the Storybook (Vue)

learn Jest (describe, it, expect) · snapshot tests · Stencil spec tests (newSpecPage) and e2e tests · Vue basics (template, props, events) · Vue 2 Options API, because the Scale Storybook uses Vue 2

build run the Scale spec tests for one component; write a test for your Stencil component first, then make it pass; start the Scale Storybook and change one story locally

One new test, red then green; Storybook runs on your machine. With your mentor, you choose your first issue.

Week 8

Your first bug fix

learn the Scale contribution rules · Conventional Commits · rebase and force-push · how a review works

build claim the issue with a comment, reproduce the bug in Storybook, write a failing test, fix it, run yarn format and lint, commit, open the PR, and @-mention a maintainer

Your PR is open and CI is green.

Why only week 1 is detailed: each next handout is written after the sync of the week before. It uses what the student showed and where they had problems. Tell the teacher agent the result of each sync; it writes the next handout.

If a week runs over: extend it. Do not skip a milestone. Weeks 2 and 5 are the easiest to shorten if needed.
