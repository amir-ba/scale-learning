Week 3: The toolchain and local Scale setup

Move from using a package to running its source project.

Time 8-10 h, including setup Start point week 2 report and promise handling work Plan all weeks Source telekom/scale

Goal: run Scale's component development server from your own clone. Change one visible text locally and see it reload. Explain the package manager, workspace and build commands that made it work.

Your calculator consumes a built npm package. The Scale repo contains the source, generators and several related packages. This week you learn to run that project. You do not need to understand all its TypeScript yet.

Before you start

At the week 2 sync, show your dependency report and clipboard error feedback. Explain a promise, a version range and the difference between bootstrap and postbootstrap. If you cannot trace those scripts, repeat that exercise before installing the larger project.

Keep the calculator and Scale in separate folders. Use npm for your calculator and Yarn 1 for Scale. Do not copy lock files or node_modules/ between them.

A: Study (2 h 45 min)

Read for the ideas, not every API option. Use the rubber duck approach. Keep only your question list, not a written summary.

  1. MDN: client-side tooling overview: 40 min.
    Look for: bundler, transpiler, formatter and linter. A formatter changes layout. A linter checks rules. Neither proves that the calculator gives correct answers.
  2. Yarn Classic: workspaces: 30 min.
    Look for: one root install, local package links and shared dependencies. Read the limits section. Yarn can hoist dependencies to the root; a package's folder does not need its own copy of every dependency.
  3. Lerna: introduction: 20 min.
    Look for: running tasks across packages. Compare with Scale's actual lerna run generate. Do not apply a modern tutorial's configuration to Scale.
  4. GitHub: contributing to a project: 30 min.
    Look for: fork versus clone, a topic branch, and the original project. Your origin will be your fork; upstream will be Telekom's repo. Do not open an upstream PR for this practice change.
  5. Microsoft: a WSL development environment: 20 min.
    Look for: a Linux terminal and Linux project storage. Under WSL, use a folder such as ~/workspaces/scale. Install and run Node.js and Yarn in that same environment.
  6. Scale root package file, component package file and contribution guide: 25 min.
    Look for: engines, workspaces, bootstrap, postbootstrap and start. Compare the live files with the commands below before running them.

A monorepo is one git repo with several packages. A workspace is a package managed as part of that root project. Compare this with a C++ solution that contains several libraries and tools, but do not assume identical dependency rules.

B: Build (4-6 h)

1. Choose one shell and check the tools (45-90 min)

On Windows, prefer WSL2. If it is not installed, use the Microsoft installation guide with your mentor. Installation can require administrator access and a restart. Git Bash is an alternative if the project's scripts work there. Do not alternate Windows and WSL tools in one clone.

The commands below use a bash-compatible shell, not PowerShell or Command Prompt. Run them in the environment where you will clone Scale:

git --version
node --version
npm --version
yarn --version

The checked Scale root file requires Node 24.x and Yarn 1.x. Use the checked-out root file as the authority if that changes. Install Node in your chosen environment using the Node.js installation instructions. If Yarn is missing, follow the Yarn Classic installation instructions; the npm method is:

npm install --global yarn@1.22.22
yarn --version

This uses npm to install the Yarn tool. It does not install Scale with npm. If an existing Yarn installation conflicts or you get a permission error, stop and check with your mentor. Do not use --force, disable TLS checks, or add administrator commands to make the error disappear.

2. Fork, clone and check remotes (30 min)

Create a fork of telekom/scale on GitHub. In your workspace folder, clone your fork. Replace YOUR-USER with your GitHub account name. These commands use GitHub HTTPS; if your existing GitHub setup uses SSH, use the equivalent SSH URLs consistently.

git clone https://github.com/YOUR-USER/scale.git
cd scale
git remote add upstream https://github.com/telekom/scale.git
git remote -v
git branch --show-current
git status
git switch -c learning/local-scale

origin must point to your fork. upstream must point to Telekom. Start the practice branch from the fork's current main. If your fork is old, sync it first using the GitHub fork-sync guide. The contribution guide still refers to master; do not create a new branch with that name to match old prose.

3. Install from the root (45-90 min)

Open the clone's root package.json. Confirm engines and the actual scripts. Predict what this command will do, then run it from the root:

yarn bootstrap

In the checked file, bootstrap runs yarn install --check-files. After success, Yarn runs postbootstrap, which starts lerna run generate. Follow the output to a workspace's generate script. Do not run generation a second time just because it is not written in the command you typed.

Use the existing yarn.lock. Do not run npm install in this repo, replace its lock file, upgrade dependencies, or suppress engine checks. Once the command finishes, inspect:

git status --short
git diff --stat

Generated output can be large. If tracked files changed unexpectedly during setup, inspect the diff and ask your mentor before staging anything. Do not use a destructive reset to hide setup problems.

4. Start the component development server (30-45 min)

In the same terminal, move into the component package and start it:

cd packages/components
yarn start

Here, start runs stencil build --dev --watch --serve --config stencil-dev.config.ts. Explain the flags: development build, watch for changes, serve locally, and use the named configuration. Open the URL printed by the terminal. Keep the terminal running.

The root package does not have the same start script. From a second terminal at the root, you could instead use yarn workspace @telekom/scale-components start. This is an alternative command, not a second server to start.

5. Make one visible local change (45 min)

  1. In a second terminal at the clone root, open packages/components/stencil-dev.config.ts. Its www output copies src/html/* to the server root. Open packages/components/src/html/index.html. This is a local test page, not the Vue Storybook.
  2. Find the visible heading whose text is index.html. Change only that text to Week 3 local check. Do not change imports, component logic or generated files. If the file moved in your checkout, follow the actual dev configuration's copy paths instead of creating a new page.
  3. Save. Watch the terminal rebuild and confirm the changed text in the browser. If it does not reload automatically, refresh once and investigate the watch output.
  4. Use git diff -- packages/components/src/html/index.html to inspect your change. Explain why installing the npm package in the calculator would not expose this local source edit.
  5. Return only your practice text to its original value with the editor. Check that the browser returns to the original text and that your one-file diff is empty. Do not discard any other changes.

This is a deliberate local experiment, not a bug fix. You do not need to publish it or open a Scale PR.

6. Build and restart (45-60 min)

Stop the server with Ctrl+C. From packages/components, return to the root and build the component package:

cd ../..
yarn build:components

Trace the root script into the component package's build script. This produces library output; it does not start the development server. Inspect git status --short again. Do not stage generated files or publish anything.

Start the same development server again from the correct folder. You must be able to stop and restart it without repeating the install. Storybook is a separate package and is planned for week 7.

Troubleshooting

SymptomCheck
Node engine mismatchCompare node --version with root engines in the same shell. Windows and WSL can use different Node installations.
Yarn 3 or 4, or unexpected package-manager outputScale asks for Yarn Classic 1.x. Check yarn --version and the installation method; do not migrate the repo.
sh, rm or a shell script cannot runUse WSL2 or Git Bash. Do not translate the repo's scripts into PowerShell as part of setup.
Command "start" not foundCheck the current folder and its package file. Start from the component package, or use the named workspace command.
Registry, certificate, proxy or binary-download failureRead the first failing command and exact error. Follow your network's approved setup; do not disable certificate verification or run random cleanup commands.
The server port is occupiedCheck whether your earlier server is still running. Reuse it or stop your own process; do not kill an unknown process.
The page does not show the editCheck the printed URL, dev entry, saved file and rebuild output. Do not edit installed npm files or the calculator's page.

30-minute rule: if setup blocks you for more than 30 minutes, send your mentor the command, working folder, tool versions and exact error. Continue with script reading where possible. Allow extra setup time instead of skipping the running-project milestone.

Done when

  • Your clone uses the Node and Yarn versions required by its root package file.
  • You show that origin is your fork and upstream is Telekom's repo.
  • Root bootstrap succeeds, including the postbootstrap generation step.
  • The component development server runs; you stop and restart it from the correct folder.
  • One source-page text change appears in the browser and is then removed.
  • The component build passes; no dependency upgrade, extra npm lock file or unrelated change is staged.
  • You explain the tool roles, workspace layout and actual setup commands without notes.

Bring to the sync

  • Your fork URL and the clone, with terminals ready for the setup and start commands.
  • The running dev page and a short demonstration of the local text change.
  • The root and component package files, current git status and your question list.
